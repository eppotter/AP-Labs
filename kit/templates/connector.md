# Adding a connector

A connector is the one way the app reaches an external system (a CRM, an email tool, billing, any API). Every connector has the same shape, declared with `defineConnector` from `#sdk`, and passes the same contract suite. The engine enforces the guardrails; the adapter only says how to talk to the system. Adding one is a folder in the app dir. No engine file (`kit/**`, `profiles/_schema/**`) changes.

Before you write one, check `.aplabs/context/connectors.md` and ask Connector: a system has one approved path per operation, and a new connection or credential is a gated human action, never created inside a build.

## Steps

1. Copy the template into the app dir, naming the folder after the connector's id:

   ```bash
   cp -r kit/templates/connector app/connectors/crm
   ```

   The template is two files: `connector.js` (the adapter) and `connector.test.js` (its test).
2. Fill in the declaration (fields below) from the system's entry in `connectors.md`.
3. Replace `connect` with the system's real client, and each operation's body with real calls. Delete the in-memory stand-in.
4. Give the contract suite one sample input per operation in `connector.test.js`, then run `npm test`.
5. Add the system's contract fields to `connectors.md` (kill switch, idempotency, batch size; see the template there) through Scribe and the owner's sign-off.

## The declaration

| Field | What it is |
|---|---|
| `id` | Lower-case slug (`crm`). Matches the folder name. |
| `system` | The system's plain name (`Acme CRM`). People see it in "switched off" and "couldn't reach" messages. |
| `auth.env` | The **names** of the env vars holding its credentials (`["ACME_CRM_TOKEN"]`), never values; `[]` for a system with no credential (a mock). Read once through `kit/lib/secrets` from the environment only (connectors never fall back to the Keychain, AD-12), cached with the client, and registered with the log so no line shows them. Only declared names can be read. |
| `killSwitchEnv` | The connector's own kill switch (`ACME_CRM_OFF`). When set, every write refuses before any I/O. |
| `rateLimit` | `{ perSecond, batchSize }` from the system's documented limits. Calls are spaced to `perSecond` (the engine waits, never drops); a request over `batchSize` is refused. A call the system refuses with status 429 is retried by the engine through the same limiter, waiting what its `Retry-After` asks (`err.retryAfter` in seconds or as a `Date`, or a `retry-after` header on `err.headers` in seconds or as an HTTP date; dates are read against the instance's clock, `now`), up to 3 attempts; a call already waiting re-checks the hold when it wakes; a wait over 60 s, or a fourth 429, fails with `ConnectorFailed`. The adapter only has to throw an error with `status: 429`. |
| `connect({ secret, registerSecret, data, simulate })` | Builds the client once per process. It may be async (an OAuth exchange): the engine awaits it, and a rejected connect is not cached, so the next call connects again; a rejection with `status` 401 or 403 is a `ConnectorAuthFailed`. `secret(name)` returns a declared credential. `registerSecret(value)` masks a token `connect` obtains itself (an OAuth access token) in errors and every log line, and returns it. On a 401 or 403 the client must throw an error with that `status` (or a `ConnectorAuthFailed`). `data` is the query runner when the connector was created with `{ data }` (a connector over the client's own data, such as a mock). The engine passes it as is: its SQL passes the guardrail and the profile's forbidden columns when it is the app's runner (`kit/runtime/data`), not when a test passes a stand-in. `simulate` is the test-only `deps.simulate`, for the adapter's own failure simulation. |
| `read.<name>(input, ctx)` | A read operation. Read-only and least privilege: fetch only the fields the call names. The engine can't see what an adapter fetches, so the contract and its suite don't check this: it is a review item for Connector on every connector. |
| `write.<name>` | `{ plan(input), apply(input, ctx) }`. `plan` says what would be written, with no I/O; `apply` writes. |

The app creates one instance per process with `connector.create({ log, ... })`; a second `create()` shares the first's idempotency state (below). `log`, the app's logger (`kit/runtime/log`), is required: `create` fails without it, so every credential the connector reads is masked in every log line (AD-12). A test passes `testLog()` from `#sdk`.

Inside an operation, `ctx` has `client` (from `connect`), `request(fn, { size })` (every call to the system goes through it), `batches(items)` (splits a list by `batchSize`), `operation`, and on a write `idempotencyKey`. Pass the key on to the system when its API takes one. For a list, give each item its own key, the write's key plus the item's id (`${ctx.idempotencyKey}:${item.id}`), never a per-batch suffix: a retry after a partial failure then resends only the items the system has not seen, however the rows are ordered or batched.

## The safe defaults

- **Writes are dry runs unless the caller says otherwise.** A write without `dryRun: false` returns `{ dryRun: true, operation, wouldWrite }` from `plan` and calls nothing. Only the approval-write archetype (`kit/runtime/archetypes/approval-write`) passes `dryRun: false` (AD-15). A module that pushes declares a `write` block in its manifest and never calls the connector itself. The write-path check (`kit/verify/write-path.js`) enforces it. It runs in `npm run check` and `npm test`, and in every `npm run verify` and the end-of-turn hook as the built-in check `engine:write-path`, which a profile can't drop: outside the archetype, the contract (`kit/runtime/connectors/`) and each connector's own folder (`app/connectors/<id>/`, the template; a loose file directly in `app/connectors/` is not one), a line that mentions `dryRun` other than `dryRun: true`, reaches a connector's `write` operations, aliases them or creates a connector instance in a file that imports a connector, or calls `defineConnector` fails the check, naming the file and line. In a governed repo it fails when it finds no app dir (`app/`, or `APLABS_APP_DIR`, which must exist). A fork relies on those two; the template repo lists its example clients' app dirs in `package.json` under `aplabs.appDirs`, which only adds dirs to scan. It is a tripwire for honest mistakes, not a sandbox: review still reads every write path.

  **For forks (DEP-012):** from this version, a module or other app code that passes `dryRun` (other than `dryRun: true`), touches a connector's `.write`, or creates its own connector instance fails `npm run check`. Move the push into a module manifest's `write` block for the approval-write archetype.
- **Two kill switches.** The connector's `killSwitchEnv` and the global `APLABS_WRITES_OFF` each refuse every write, dry runs included, with `KillSwitchOn`, before credentials are read. Any non-empty value is on, even `0` or `false`: unset it to turn writes back on. Reads keep working. The env is read on every call and again before every request a write makes, so a switch takes effect at once: flipped partway through a push, it refuses the batches still to come (the write fails with `KillSwitchOn` and does not use up its key).
- **Resuming a stopped write.** When a live write stops partway (a kill switch, an outage, a rejected sign-in), the engine records each request that went, as it stops, in the idempotency store beside the write's slot (at `<connector id>\u0000<operation>\u0001progress\u0000<key>`, holding `{ input, partial: true, batchSize, completed: [{ size, result }] }`; a durable store must keep that value whole and return the latest one set, or the retry fails closed; a write that completes stores nothing extra, and a process that dies mid-write records nothing). A retry with the same key and input runs `apply` again: the recorded requests get their recorded answers without calling the system, and only the rest are sent, so nothing is sent twice. Another input under the key, or the same input after `batchSize` changed, is refused with `IdempotencyConflict`; a resumed request whose size changed fails with `ConnectorFailed`. So `apply` must make the same requests, in the same order and sizes, for the same input, and a durable `idempotency` store must be able to hold the requests' answers. The error carries `details.sent` (`{ batches, items }`, items summed from the requests' `size`) and the person is told how many went, never "nothing was sent". After a `PartialFailure`, a write that declares `perItemIdempotency: true` drops the record so its retry re-sends (the system keeps only the items it lacks); any other write keeps it, so its retry sends nothing again and fails the same way until someone looks.
- **Idempotency.** Every write needs an `idempotencyKey`. A repeated key with the same input returns the first result and calls nothing; a failed write does not use up its key. The input is fingerprinted under its key, so a reused key with a different input is refused with `IdempotencyConflict` (a `ConnectorFailed`) and calls nothing. Keys live in memory for the process unless the connector is created with `idempotency: { get, set }` (a mock's outbox, or a durable store); the store holds `{ input, result }` per slot (or, for a write stopped partway, its progress record: see below), `<connector id>\u0000<operation>\u0000<key>`, so one store can serve several connectors. (The slot gained the connector id with DEP-012: records an older version stored under `<operation>\u0000<key>` no longer match, so clear a durable store, or delete an old local `var/outbox/email.jsonl`, when you upgrade.) The in-memory store is one per connector, shared by every instance its `create()` makes in the process, so a second instance sees the keys the first applied and a concurrent repeat on another instance joins the first write instead of applying again. Instances given the same `idempotency` object share their in-flight writes the same way. The store is per process: across processes or restarts only a durable `idempotency` store (or the system's own dedupe) protects a key.
- **Fail closed.** A missing credential or an auth error from the system fails the call with `ConnectorAuthFailed`; a read never returns empty or partial data instead. Any other failure is a `ConnectorFailed`.
- **No credential in an error.** Every error is rebuilt from a redacted message: the connector's credentials, tokens passed to `registerSecret`, `Bearer` and `Basic` headers, `token=`-style values (in a query string or bare in text), passwords in URLs, JSON fields named like a secret (`api_key`, `token`, `secret`, `password`, `client_secret`, `access_token`, `refresh_token`, `id_token`, ...), `X-Api-Key:`-style headers and any `Authorization` value (`Token`, `Basic`, `Bearer` or none) are masked. The original error is not kept, so nothing on it leaks.
- **Partial failure.** When a list write partly applies (the system took some items and refused others), throw `PartialFailure` from `#sdk` in `apply`: `throw new PartialFailure(reason, { succeeded, failed, failedRefs })`. `failedRefs` is the failed items' external ids, one per failed item, never contact data. An id-shaped ref has a digit and only letters, digits and `. _ : -` (`c_123`, `CRM-00042`, a UUID, a short number); anything else is masked, including an email, a word with no digit (a name) and 7 or more digits with only separators (a phone number, a date). Put counts only in `reason`: the engine drops the adapter's text anyway and rebuilds it from the counts, so refs and contact data can't leak through it. The engine logs the counts and refs as a warning and the person sees only the counts. By default the message asks them to tell the admin before trying again: the engine can't know a retry is safe. Declare `perItemIdempotency: true` on the write (`{ plan, apply, perItemIdempotency: true }`) only when each item is keyed (above) and the system adds only keys it hasn't seen, so a retry with the same key and input re-sends only the failed items; then `details.retrySafe` is true and the message says trying again is safe. The suite then needs a `samples.bulk` for the write and checks a retry after a failed batch succeeds; your own test must show each item lands once. Counts that don't add up, or a `PartialFailure` from a read (a read fails whole), become a plain `ConnectorFailed`.

`kit/runtime/messages` turns `KillSwitchOn`, `ConnectorFailed`, `ConnectorAuthFailed`, `IdempotencyConflict` and `PartialFailure` into a plain message for the person; the reason goes to the log only. A missing credential (a setup fault) and a credential the system rejected get different messages, and neither says to try again later. `messageFor(err, { admin })` names the admin to tell when the caller knows it, else "your admin".

## The contract suite

`connectorContract(connector, samples)` from `#sdk` registers the shared tests: the declaration, dry run, both kill switches, idempotency, the rate limit, batching, fail-closed reads and redacted errors (the declared-credential checks are skipped for a connector with `auth.env: []`, with a diagnostic line saying so; the credential-shape check runs for every connector). It runs the connector with fake credentials, a fake clock and a fake system failure, so it never needs the real system. `samples.read` and `samples.write` must cover every operation; `samples.bulk` (`{ operation, input(count, key) }`, or a list of them) must cover every write whose sample has a list in it: the suite sends `2 × batchSize + 1` items and checks each request is within `batchSize` and says its size (`ctx.request(fn, { size })`), so a write that sends a whole list in one call fails. A third argument's `deps` is passed to every instance the suite creates, for what the connector needs besides credentials (for example `{ deps: { data } }` with a stand-in runner); the suite's own env, clock and `onRequest` still win.

## Connector code is trusted, not sandboxed

Like a module handler, a connector is trusted, reviewed code that runs in the app's process and can reach `process.env`. Review it as engine code: never log a credential, never put one in an error, and keep every call inside `ctx.request`.
