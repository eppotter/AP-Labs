- (capability) CAP-2 Hubs and registry: each hub is a slash command whose Block Kit menu is built from registry data; adding an entry is data only; success = test builds menus from fixture entries, clicking dispatches the right handler, hidden entries rejected at dispatch too
- (capability) CAP-3 Module contract: a module is one manifest (hub, label, resource key, archetype, params) plus one handler; malformed manifest fails the check; success = module template copied and filled appears in its hub with no engine edit; contract test rejects bad manifests
- (capability) CAP-4 Access wiring: menu visibility and every dispatch check kit/lib/permissions against the profile via the user's slack identity; deny beats allow; unknown user and config fault are told apart from denial; success = tests per allow/deny/unknown/misconfigured key
- (capability) CAP-5 LLM service: one Claude client with prompt assembly from profile + .aplabs/context, tool definitions and dispatch, an hourly spend breaker and kill switch; tests never call a model; success = stubbed-client tests cover prompt assembly, tool dispatch, breaker trip, kill switch, timeout
- (capability) CAP-6 Connector pattern: every external system adapter has one shape (auth from named env vars, read vs write ops, dry-run, idempotency key, kill switch, rate limit) and passes one shared contract test; success = contract test suite runs against the mock and a template adapter
- (capability) CAP-7 Mock connector: Brightside mock CRM (look up, update client) and mock email tool (create list, add contacts) over the fixture; writes land in an inspectable local outbox, never the fixture; success = contract tests pass; pushes are idempotent; outbox shows what arrived
- (capability) CAP-8 SQL guardrails: generated SQL is single-statement read-only, blocked on forbidden columns from the profile (incl. wildcard select when any are configured), fails closed on unterminated input; success = tokenizer tests incl. CTE, comment-in-literal, TOP n *, quoted star, DDL/DML, multi-statement
- (capability) CAP-9 Scoped pull archetype: one parameterised engine turns a plain-English request into the module's declared parameters, confirms them with the user, runs a guarded query and delivers results privately; success = scripted conversation on the fixture yields expected parameters and rows; modules configure, never clone, the engine
- (capability) CAP-10 Approval-gated write archetype: preview (count, sample, destination) then approve via opaque single-use user-bound expiring token, then push with idempotency, partial-failure report and suppressed escalation; success = tests cover approve, cancel, expiry, wrong user, double click, partial failure, kill switch
- (capability) CAP-11 Slack UX basics: thread context, markdown to Slack with long-output chunking, provenance button (parameters + SQL), first-run onboarding and help per hub, TTL cache; private delivery by default; success = unit tests per helper; provenance shows the exact SQL run
- (capability) CAP-12 Scheduled jobs: a declarative cron registry (name, schedule, run, enabled flag) runs entries with logged start/finish/failure; template ships no jobs; success = tests with fake clock show enabled runs, disabled skips, a failing job logged and not crashing the app
- (capability) CAP-13 Brightside fixture: Tier-1 synthetic dataset generated deterministically into versioned seed files, built offline into local DuckDB for dev/CI, validated (integrity, synthetic-only, known truths), publishable to MotherDuck by Ely; success = same seed gives identical files; build offline < 60s; validation passes; CI needs no network
- (capability) CAP-14 Demo flow: in a fresh fork configured for Brightside, a person in Slack goes plain-English request -> scoped pull -> scoring -> approval -> push to the mock email tool; scoring deterministic with per-row reasons; success = end-to-end acceptance test through fake Slack, fixture and mock passes in CI; Ely runs it live
- (capability) CAP-15 Fork acceptance: two forks differ only in profile and their own modules; success = acceptance test builds two forks from fixture profiles, engine files identical, each boots its own hubs and access
- (constraint) Runtime is Node 20 and bash (ADR 0002); only the fixture toolchain is open
- (constraint) Slack is the only surface; module contract stays surface-agnostic in shape (TA-17) but V1 ships only the Slack adapter
- (constraint) Consumer surface is menus and typed forms, not an open chat box (TA-18); plain English enters through a module's input, never a free-roaming conversational agent
- (constraint) Private delivery by default (DM or ephemeral); any channel delivery is a declared, tested exception
- (constraint) Each new profile key lands with the story that reads it (PLAN §2), validated by the schema with unknown keys rejected; the profile never holds secrets
- (constraint) Secrets (Slack tokens, LLM key, MotherDuck token) come from env or the macOS Keychain at runtime; never in profile, repo, logs or agent-visible output; startup errors name the variable, never its value
- (constraint) Tests and CI are offline and deterministic: no Slack, no model, no MotherDuck; fakes and stubs only; the fixture DB is built from committed seed files
- (constraint) Synthetic data only: fictional names, emails on .invalid, phones 555-01xx; no client or production data; validation fails the build otherwise
- (constraint) Generated SQL is read-only and passes the guardrails before it runs; writes to external systems go only through a connector via the approval-gated archetype
- (constraint) Scoring is deterministic and explainable (declared weights, per-row reasons); no LLM in the score
- (constraint) One parameterised engine per archetype; modules configure it and never clone it (TA-16)
- (constraint) Every LLM call passes the spend breaker and kill switch; the bot degrades with a plain message, never a silent failure
- (constraint) Engine vs instance: engine code is identical across forks; client hubs, modules and profile are the only per-fork files; Brightside demo modules ship as examples, not engine
- (constraint) Dependencies pinned exactly with a one-line reason each (PLAN §3): Slack Bolt, DuckDB, the Anthropic SDK are expected
- (constraint) No Hometown specifics in code, docs or fixtures outside docs/reference/; Varsity is read for patterns only, never copied verbatim with its canon
- (decision) Non-goals: real client connectors or CRM vendor; production warehouse or data; surfaces beyond Slack; archetypes beyond scoped pull and approval-gated write; conversational chat agent; FAST lane; durable session store beyond in-memory; cost rollups/dashboards; production hosting choice; real cron jobs; Teams/web
- (decision) Seed data is versioned as committed generated files plus the generator; CI regenerates and fails on any diff, so the data is reviewable and the generator stays deterministic
