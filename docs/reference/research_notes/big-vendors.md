# Major Platform Vendors' Enterprise AI Agent Offerings — Governance, Permissions, Review, Lifecycle

**Research date: 2026-10-22.** All "current status" claims are as of that date. Statuses below are explicitly marked SHIPPED/GA, PREVIEW, or ANNOUNCED where the source supports it, and flagged as unknown where it does not. Microsoft Learn pages carry visible `ms.date` / `updated_at` stamps, which are quoted so the report-writer can judge staleness.

## Microsoft: Copilot Studio / Microsoft 365 Copilot agents / Agent 365

### Takeaway
Microsoft has by far the deepest and most *documented* lifecycle story, because it inherited Power Platform ALM wholesale: real dev/test/prod environments, solution-based promotion, Git integration, CI/CD, plus a tenant-level Agent Registry in the M365 admin center with an actual admin approval gate ("activation"), 30-day soft delete, and audit logging. The weak seam is that nearly all *quality* gating is advisory guidance prose rather than enforced machinery, and the governance depth is tiered by license — much of it requires M365 E7 or a standalone Agent 365 subscription.

### Cited Findings — Architecture, definition, storage, versioning
- Copilot Studio agents are always created and managed inside Power Platform environments, which "act as logical containers that define data boundaries, security roles, data policies, and lifecycle separation" — [Implement a zoned governance strategy, Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase2) (`ms.date` 2026-01-16; `updated_at` 2026-10-15)
- ALM is defined as covering the agent "from the initial idea and requirements gathering ... through development, testing, deployment, and ongoing maintenance until decommissioning" — [Establish an ALM strategy, Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/alm) (`ms.date` 2026-01-16; `updated_at` 2026-09-12)
- "A healthy ALM strategy includes at least three environments: development, test, and production." Production must be configured as a *production type* environment; dev and test as *sandbox type* — [ALM strategy](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/alm)
- Transport mechanism is **solutions** (containers for artifacts), with **environment variables** for per-environment settings/secrets and **connection references** for per-environment credentials. Native **Git integration** via Dataverse is supported — [ALM strategy](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/alm)
- ALM "golden rules" include: "Don't customize outside of a development environment"; "Always work in the context of solutions"; "Export and deploy solutions as managed, unless setting up a development environment." Managed solutions are read-only downstream, which structurally prevents edits in test/prod — [ALM strategy](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/alm)
- **Documented leak in the model:** several Copilot Studio items are *not solution-aware* and require manual post-deployment steps in the downstream environment — Azure Application Insights settings, manual authentication settings, Direct Line / Web channel security settings, deployed channels, and **sharing (with makers or end users)** — [ALM strategy](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/alm)
- Three ALM automation options with explicit skill-floor framing: **Azure DevOps** ("Setup complexity: High (requires configuration and expertise)"), **GitHub Actions for Power Platform** ("Moderate"), **Power Platform Pipelines** ("Low (few minutes setup)", "Best for: Organizations empowering citizen developers") — [ALM strategy](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/alm)
- GitHub Actions path includes "Static analysis checks using Solution Checker" — the only static-analysis gate named in the comparison table — [ALM strategy](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/alm)
- **Component collections** (reusable topics, knowledge, actions, entities) can be versioned and moved across environments to support "independent release cadences"; best practices explicitly list "Version control: Track versions for consistency and rollback" — [ALM strategy](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/alm)

### Cited Findings — Who builds (the zoned model, and the real skill floor)
Microsoft's own doc segments agent creation into three zones "based on the purpose of an agent and its risk level":
- **Zone 1 — Citizen Development Zone:** "Anyone can make personal and team productivity agents based on content they already have access to. Agents have read-only permissions and stay private." Tools: Agent Builder in Microsoft Copilot, SharePoint agents. Governance: Developer environments, environment routing to keep agents isolated to the maker, **sharing disabled** — [sec-gov-phase2](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase2)
- **Zone 2 — Partnered Development Zone:** "IT-approved makers build agents for use by other teams and departments... Agents follow IT-managed review processes and are deployed to secure, IT-managed environments." Tool: Copilot Studio. Governance explicitly lists "Application Lifecycle Management (ALM) **pipelines** for agent versioning" and "**IT-admin approval to publish agents**" — [sec-gov-phase2](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase2)
- **Zone 3 — Professional Development Zone:** "Pro developers build mission-critical, enterprise-grade agents... uses organizational standard ALM practices and the strongest security controls." Tools: Microsoft Foundry Agent Service and Copilot Studio. Zone 3 agents "Can have Service Level Agreements" — [sec-gov-phase2](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase2)
- Zone 2 is described as built by "trained citizen developers" who "require formal assistance and oversight from a coach" — i.e., Microsoft's own documentation concedes the mid-tier requires a human coach, not just a no-code tool — [sec-gov-phase2](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase2)

### Cited Findings — Permissions and data access
- Zone 1 agents "run in user's context only" and are limited to "Only Microsoft 365 and Power Platform connectors" — [sec-gov-phase2](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase2)
- Three enforcement levels (tenant / environment / agent). Tenant-level data policies can allow or block: unauthenticated usage, individual channels, **knowledge sources**, individual connectors, Azure Bot Service skills, Application Insights integration — and can "Allow or block publishing of agents that use generative AI" — [sec-gov-phase2](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase2)
- Environment level adds advanced connector policies, blocking the public data source (e.g. Bing), VNet support and IP firewall. Agent level toggles generative orchestration, AI knowledge, generative answers, and sets authentication mode — [sec-gov-phase2](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase2)
- Maker access is controlled by Dataverse security roles over the `Copilot`, `Copilot Subcomponent`, and `Conversation Transcript` tables. "Users with a System Administrator role can read and update all agents and transcripts" — [sec-gov-phase2](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase2)
- **Documented fail-open/fail-opaque behavior:** admin actions initiated from the M365 admin center **fail** against agents in environments running Power Platform Firewall in *active enforcement mode*, because "the IP address is the upstream service IP rather than the originating admin client IP, so the firewall rejects the request." In *audit-only* mode the action succeeds and only raises a Purview alert. Remediation is to call the Power Platform API directly, including `admin-api-quarantine` and `admin-api-reassign-ownership-orphaned-agent` — [Governance and Lifecycle actions for agents, Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions?view=o365-worldwide) (`ms.date` 2026-09-23; `updated_at` 2026-10-13)

### Cited Findings — GOVERNANCE AND LIFECYCLE (the M365 Agent Registry)
SHIPPED actions in the Microsoft 365 admin center, per [agent-actions](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions?view=o365-worldwide):
- **Activate** = a real pre-use approval gate: "Activation is a governance step for new agents. When a user requests activation so they can create instances of an agent, the request requires **AI admin approval** before the requester can create instances. Administrators review the agent's details, such as its description, owner, data, and tools, and then approve or reject the request."
- Activation flow is an eight-step wizard with a **Requests** tab listing pending submissions (agent name, publisher, status, date requested), review of "description, capabilities, connected data sources, and tools," audience scoping to users/groups/everyone "to ensure a controlled rollout," and a permission review with explicit **Grant admin consent**.
- **Policy templates** bind governance to activation. The Microsoft-provided **default template** attaches: Entra Identity Protection for agents, Entra network visibility, Entra **lifecycle management for Agent IDs**; SharePoint external-sharing restriction, site access control, content permissions insights, agent access insights; Purview **audit enabled**, "Know your data" policy, **AI compliance assessment**; Defender investigation/advanced hunting and **real-time protection (Preview)**. A **custom template** can add further policies.
- Noted limit: "AI Administrators aren't authorized to configure Conditional Access policies or Microsoft Entra access package policies. These actions require a highly privileged administrator role."
- **Publish to store / Reject submission** — an admin can publish a *requested* agent to the Agent Store or reject it.
- **Block / unblock** org-wide. Scope caveat: blocking a Copilot Studio or Agent Builder agent affects Copilot and host apps (Outlook, Teams), but "blocking an agent that you created by using SharePoint or Microsoft Foundry only impacts its availability in Microsoft Copilot Chat."
- **Soft delete with a 30-day recovery window**, then restore or permanently delete; retained properties include "the agent ID, metadata, channels, ownership, and connections." Critically: "Soft-delete, restore, and permanent-delete events are recorded in the **audit log** with information about the system that initiated the action."
- **Ownership lifecycle:** assign a new owner to ownerless or active agents; Agent Builder agents support multiple co-equal owners ("There are no primary or secondary owner roles"); "You can't remove the last remaining owner." Rationale given: "Multiple owners reduce reliance on a single person."
- **Start/stop** the underlying Azure infrastructure for Foundry agents (requires Azure AI Owner role).

### Cited Findings — Agent 365 (the control plane) and license-gating of governance
- "Microsoft Agent 365 is a Microsoft 365 service that provides a centralized control plane for AI agents... discover, manage, govern, and secure agents" including "agents built or acquired from third-party sources" — [Microsoft Agent 365 service description](https://learn.microsoft.com/en-us/office365/servicedescriptions/microsoft-agent-365/microsoft-agent-365) (`ms.date` 2026-09-30; `updated_at` 2026-10-01)
- Packaging: "available as a stand-alone subscription for use with eligible Microsoft 365 subscriptions and is also included with **Microsoft 365 E7**" — [Agent 365 service description](https://learn.microsoft.com/en-us/office365/servicedescriptions/microsoft-agent-365/microsoft-agent-365)
- **Included with base Enterprise/Business/Education/FLW plans:** inventory of agents in the Agent Registry; basic governance actions (publish, deploy, block, delete, approve, assign to users/groups, reassign owner, pin); "**Automate agent lifecycle actions using conditions-based rules**"; synchronize agents and metadata from external, non-Agent-365-managed platforms into the registry — [Agent 365 service description](https://learn.microsoft.com/en-us/office365/servicedescriptions/microsoft-agent-365/microsoft-agent-365)
- **Requires E7/G7 or Agent 365 add-on:** policy templates; observability and monitoring of agent activity; tenant-wide control over which tools (including Microsoft MCP servers) agents can access; Graph API access to the registry and governance actions; Entra access packages for agent permission scope; Entra sponsor-driven lifecycle policies; conditional access and identity protection for agents; Purview audit logs + eDiscovery of agent interactions, Data Lifecycle Management for agent-generated data, compliance assessment, DSPM with AI Observability, Insider Risk Management for agents, sensitivity-label inheritance, DLP blocking agents from sensitive content; Defender shadow-AI endpoint agent sync, misconfiguration/exposure remediation with relationship mapping, tool-invocation blocking; Intune device compliance for agent conditional access, policy-controlled agent runtime, blocking unsanctioned local endpoint agents — [Agent 365 service description](https://learn.microsoft.com/en-us/office365/servicedescriptions/microsoft-agent-365/microsoft-agent-365)
- Several high-value Purview/Defender/Intune rows are marked **"GCC Availability: No"** — [Agent 365 service description](https://learn.microsoft.com/en-us/office365/servicedescriptions/microsoft-agent-365/microsoft-agent-365)
- Compliance status: "As of October 1, 2026 Microsoft Agent 365 meets all FedRAMP High controls reviewed by Microsoft's independent third-party assessor. **Final authorization by Microsoft's accrediting agency is pending.**" — [Agent 365 service description](https://learn.microsoft.com/en-us/office365/servicedescriptions/microsoft-agent-365/microsoft-agent-365)
- Multi-tenant blocking is supported for tenants under an Entra Tenant Governance relationship — [Manage agents across multiple tenants](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-multi-tenant?view=o365-worldwide)

### Cited Findings — Evaluation and verification
- Microsoft's testing guidance enumerates eight test types: development-time (unit), core scenario ("happy path"), knowledge, **regression**, **adversarial** ("edge cases, queries with unknown intent, or false information"), performance/load, security and compliance (RBAC, conditional access, sensitivity label enforcement, no confidential data leaked), and accessibility/UX — [Design a testing strategy for your agents](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase4) (`ms.date` 2026-01-16; `updated_at` 2026-09-12)
- Built-in evaluation: Copilot Studio supports creating a **test set** whose cases can be hand-written, "generate[d] from the agent's instructions, capabilities, and knowledge," or populated from past test-chat conversations. Three methods: **text match**, **similarity**, and **quality** — where quality "[d]etermines the general quality of an agent response by using key criteria such as relevance, **groundedness**, completeness, and abstention" — [sec-gov-phase4](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase4)
- Bulk/at-scale testing is delivered through the **Copilot Agent Kit** test automation suite ("response match, topic match, and multi-turn" test types) — a kit, not core product — [sec-gov-phase4](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase4)
- **The gating language is advisory, not enforced:** "Always run tests before deployment to the production environment and **consider** including automated testing as part of your deployment pipeline"; principles are "Shift-left testing," "Test before production," "**Automate where possible**" — [sec-gov-phase4](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase4)
- Sprawl remediation tooling exists: the Copilot Studio Kit's **Compliance Hub** "continuously evaluates agent configurations collected via Agent Inventory against configurable risk thresholds, automatically creating compliance cases when violations are detected," with enforcement actions of manual review, **quarantine**, or delete — [Copilot Studio Kit overview, Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/kit-overview)
- The 2025 Wave 1 release plan frames agent inventory partly as hygiene: find "custom agents created by users who left" and "inactive agents to clean up" — [Search and inventory custom agents, Power Platform release plan](https://learn.microsoft.com/en-us/power-platform/release-plan/2025wave1/power-platform-governance-administration/search-inventory-custom-agents-copilot-studio)

### Cited Findings — Deployment surfaces, pricing, complaints
- Surfaces: Microsoft 365 Copilot, Teams, Outlook, SharePoint, the Agent Store, Copilot Studio channels (including Direct Line / web channel), and Foundry-hosted agents — [agent-actions](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions?view=o365-worldwide)
- Pricing (third-party, unverified against Microsoft's current price list): Copilot Credits at roughly **$0.01/credit pay-as-you-go** and ~$0.008 prepaid, with a 25,000-credit pack around $200/month on annual commitment, and credits that do not roll over month to month — [Copilot Studio Pricing in 2026: What Credits Actually Cost, coworker.ai](https://coworker.ai/blog/copilot-studio-pricing); [Copilot Studio Licensing Guide, samexpert](https://samexpert.com/copilot-studio-licensing-guide/)
- The unpredictability complaint is structural: published per-interaction rates of ~1 credit for a scripted answer, 2 for a generative answer, 5 for an agent action/connector call, with reasoning models far higher — so a single user message can range from 1 to 200+ credits depending on how the agent was built — [Copilot Studio Message Pricing & Cost Control 2026, thenegotiationexperts](https://thenegotiationexperts.com/blog/copilot-studio-message-pricing-costs/); [getmacha](https://www.getmacha.com/blog/copilot-studio-pricing-explained)
- One third-party review claims that at 125% of prepaid capacity Microsoft disables custom agents and end users see a billing-issue message. **Unverified against Microsoft docs** — [a8gent](https://a8gent.com/platforms/copilot-studio)
- Adjacent but **distinct product**: Visual Studio Magazine documents sustained credit-billing complaints after a June 1 billing change, with a GitHub Community poster saying unpredictable costs made Copilot "feel risky to use instead of helpful." This is **GitHub Copilot**, not Copilot Studio — do not conflate — [Copilot Credit Complaints Keep Coming: 'Too Expensive to Use', Visual Studio Magazine](https://visualstudiomagazine.com/articles/2026/08/07/copilot-credit-complaints-keep-coming-too-expensive-to-use.aspx); [Copilot Billing Shock Hits Developers](https://visualstudiomagazine.com/articles/2026/06/04/copilot-billing-shock-hits-developers.aspx)

### Inferences
- Microsoft's zoned model is the closest thing any vendor ships to a **risk-tiered** build process — but the tier is assigned by *which tool the maker chose*, which is self-selected. Nothing computes blast radius from what the agent actually touches, so a maker can stay in Zone 1 while attaching a sensitive SharePoint site they happen to have access to.
- The non-solution-aware list is a real governance hole: **sharing** is not carried by solutions, so the single most consequential production setting (who can see the agent) is set by hand in prod outside the ALM pipeline.
- Governance is license-stratified. An org on base M365 gets inventory + block/approve but **not** policy templates, observability, tool/MCP restriction, Purview audit of agent interactions, or DLP for agents. A "we have Microsoft governance" claim is only true at E7/Agent 365.
- The Power Platform Firewall interaction is a concrete example of the failure mode the benchmark targets: an admin control that silently does not apply, where the safe mode (audit-only) is also the permissive mode.

## Google: Gemini Enterprise / Gemini Enterprise Agent Platform

### Takeaway
Google rebuilt and renamed its agent stack as the **Gemini Enterprise Agent Platform** at Cloud Next on 2026-04-22, organized into Build / Scale / **Govern** / Optimize pillars. The Govern pillar (Agent Identity, Agent Registry, Agent Gateway) and the Optimize pillar (Simulation, Evaluation, Observability, Optimizer) are genuinely strong on *runtime* control and *continuous* evaluation. But the primary documentation describes **no pre-publication approval workflow and no rollback procedure**, and the versioning primitive (agent revisions + traffic splitting) was still in public preview as of the release notes.

### Cited Findings — Architecture, definition, storage, versioning, execution
- Three authoring paths: **Agent Studio** (low-code, visual; renamed from Vertex AI Studio on 2026-04-22), the **Managed Agents API** (config-driven, REST-first), and the **Agent Development Kit (ADK)** (code-first). ADK-built agents run on **Agent Runtime** — [Agents overview, Gemini Enterprise Agent Platform docs](https://docs.cloud.google.com/gemini-enterprise-agent-platform/agents); [Introducing Gemini Enterprise Agent Platform, Google Cloud blog](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform)
- Agent Studio logic can be **exported to ADK** for full-code work — the documented low-code→code escape hatch — [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform)
- **Agent Registry** is a "queryable, centralized store" for the customer's agents, Google's agents, third-party agents, and MCP servers, capturing metadata such as "versions, frameworks, and capabilities" — [Agents overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/agents)
- State: **Sessions** store conversation history (with Custom Session IDs to map to internal records); **Memory Bank** stores long-term user information with new Memory Profiles — [Agents overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/agents); [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform)
- Execution: **Agent Runtime** ("fully managed," sub-second cold starts, multi-day long-running agents), **Agent Sandbox** (hardened environment for model-generated code and computer-use tasks), **Workspaces** (sandboxed bash/file environment isolated from core systems), batch and event-driven agents over BigQuery and Pub/Sub, bidirectional WebSocket streaming — [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform)
- Strategic lock-in note: "all Vertex AI services and roadmap evolutions will be delivered exclusively through Agent Platform rather than as a standalone service" — [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform)

### Cited Findings — Permissions, identity, and runtime enforcement
- **Agent Identity** gives each agent a **SPIFFE-formatted ID that can receive IAM permissions** — i.e., agents are first-class IAM principals, not impersonations of a user — [Agents overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/agents)
- Google's framing: each agent gets "a unique cryptographic ID, creating an auditable trail for every action mapped back to defined authorization policies" — [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform)
- **Agent Gateway** sits in the path of agent traffic, "intercepting calls to tools or other agents," and "enforces access control policies and **Model Armor** inspection of tool calls" — [Agents overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/agents)
- Three admin consoles divide responsibility: the **Agent Platform console** for platform and security administrators (agent lifecycle oversight), **Gemini Enterprise Admin** for adding/managing agents within an instance (integrating Registry and Gateway), and the **Workspace Admin Console** for governing agent interaction with Workspace services and data — [Agents overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/agents)
- At Gemini at Work 2026 (October 2026) Google framed governance as four questions — who the agent is, what it may do, what it did, and what it should never touch — answered with "identity and policy management, authorization and permission controls, secure sandboxing, network gateways," plus "built-in cost controls" — [Welcome to Gemini at Work 2026, Google Cloud blog](https://cloud.google.com/blog/products/ai-machine-learning/welcome-to-gemini-at-work-2026)

### Cited Findings — Evaluation and verification (Google's relative strength)
- **Agent Simulation**: "Tests agents against synthetic users and virtualized tools," scored on **task success and safety** — the only vendor-shipped simulated-adversary harness found in this research — [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform)
- **Agent Evaluation**: "Continuous multi-turn autoraters on live traffic" — i.e., LLM-judge based, running in production — [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform)
- **Agent Optimizer**: "Clusters real-world failures and suggests refined system instructions" — automated failure triage feeding back into the agent definition — [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform)
- **GenAI Evaluation Service**, including online evaluations using **Auto SxS** (side-by-side) — [Agents overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/agents)
- **Agent Observability**: dashboards and execution traces for debugging — [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform)

### Cited Findings — Deployment surfaces, pricing
- The **Gemini Enterprise app** is the employee-facing delivery surface for agents; **Agent Garden** supplies curated templates (code modernization, financial analysis, economic research, invoice processing); **Model Garden** offers 200+ models including Gemini 3.1 Pro/Flash Image, Gemma 4, and Anthropic Claude Opus/Sonnet/Haiku — [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform)
- Pricing (third-party; conflicting, **not confirmed against Google's price page**): Business edition from **$21/user/month capped at 300 seats**; Standard and Plus from **$30/seat**, unlimited seats. Business includes connectors and a no-code **Agent Designer**; Standard/Plus add advanced security, governance, and support for custom and third-party agents. Consumption (agent compute, model usage) is billed **on top of seats**, with small monthly free tiers such as the first 50 vCPU-hours of Agent Compute — [Gemini Enterprise Pricing 2026, agentmarketplace.ai](https://agentmarketplace.ai/blog/gemini-enterprise-pricing); [workagent.ai](https://workagent.ai/gemini-enterprise-pricing); [Gemini Enterprise Pricing, cobry.ai](https://cobry.ai/articles/gemini-enterprise-pricing)
- Sources disagree on whether Google publishes per-seat prices at all, and one lists Plus at $50/seat annual — [Gemini Enterprise Pricing 2026, coworker.ai](https://coworker.ai/blog/gemini-enterprise-pricing)

### Inferences
- Google's design philosophy is **runtime containment over pre-release gating**: identity, a policy-enforcing gateway on every tool call, anomaly/threat detection, and continuous autoraters on live traffic. The implicit bet is that you cannot review your way to safety, so you instrument and intercept instead.
- That is the inverse of the benchmark's bet. Google answers "what happens when an agent is wrong?" with *detect it in production and cluster the failure*; the benchmark answers it with *don't let it reach production unreviewed*. These are complementary, not redundant.
- Governance that is license- and edition-gated (custom/third-party agent support only on Standard/Plus) plus a 300-seat cap on the cheap tier means the no-code entry point is deliberately the least-governed one.
- That revisions/traffic-splitting — the staged-rollout mechanism — was still public preview in mid-2026 while the Registry went GA suggests Google shipped *inventory* before it shipped *safe change*.

## Salesforce: Agentforce

### Takeaway
Salesforce has the cleanest conceptual separation of **deploy from release** — agents are versioned metadata, deployment does nothing until a system administrator explicitly *activates* a version — plus a real batch regression-testing product (Testing Center) and rich session-level tracing. But Salesforce's own architecture guidance documents **no formal human approval workflow**, and Agentforce carries the heaviest external criticism of any vendor here on pricing volatility, deployment cost, and stalled adoption.

### Cited Findings — Architecture, definition, storage, versioning
- "Agentforce defines agents through metadata." The full definition, including prompts and tools, is captured in a file stored in source control such as Git, which serves as the single source of truth. AFDX retrieves metadata including **Bot**, **BotVersion**, and **GenAiPlannerBundle**, which reference the agent's topics and actions — [The Agent Development Lifecycle, Salesforce Architects](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html)
- Versioning discipline: "Each change or enhancement should be a new version." Test the new version in a sandbox without affecting the live agent, then publish and activate it to replace the prior version — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html)
- **Deploy ≠ release:** "Deployment does not make an agent live. A system administrator must explicitly 'activate' it," separating release from deployment — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html)
- Active-version limits depend on agent type; only **one** active version is allowed for the Agentforce (Default) type — [Update Agentforce Concepts, Salesforce Trailhead](https://trailhead.salesforce.com/content/learn/modules/agentforce-specialist-certification-maintenance-summer-25/get-up-to-date-on-agentforce-concepts)
- Environment path: **scratch org** (initial development with Agent Builder and AFDX; CI/CD can run unit tests and code analysis) → **full or partial sandbox** (testing with realistic data; "Knowledge sources must be ingested and re-indexed for RAG") → **production** (change sets, Metadata API, or AFDX) — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html)
- **Rollback** = "activate the last known good version" if a newly activated version misbehaves — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html)
- **Canary releases**: "send a new version to a small user subset first, enabling real-world monitoring before full rollout" — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html)

### Cited Findings — Who builds
- **Developers** use AFDX and the Python SDK for the inner loop: specs, actions, RAG pipelines, CI/CD. **Administrators** use Agent Builder and the Testing Center, and admins are responsible for activation. The guidance notes that the agent development lifecycle "requires broader skills across data science, ML engineering, and agent development" — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html)
- Independent reviews report that "effective deployment requires significant Salesforce admin and developer expertise" — [Salesforce Agentforce Reviews 2026, oliv.ai](https://www.oliv.ai/blog/salesforce-agentforce-reviews-analyzed)

### Cited Findings — GOVERNANCE AND LIFECYCLE
- Because agents are metadata, they move via standard Salesforce release machinery — change sets, Metadata API, or AFDX — and CI/CD pipelines "promote agents through environments and run end-to-end tests at each stage as a quality gate" — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html)
- **No formal human approval workflow is described.** Per the architecture guidance as read, "the closest controls are the automated E2E quality gates and the explicit activation step" — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html)
- Salesforce positioned Testing Center as "Agentic Lifecycle Management," covering "the whole thing from genesis to development all the way through deployment, and then iterations of your deployment" — [Salesforce Introduces Agentforce Testing Center, Salesforce Newsroom, 2024-11-20](https://www.salesforce.com/news/press-releases/2024/11/20/agentforce-testing-center-announcement/)
- Launch status history: "Agentforce Testing Center is in a closed pilot today, and will be generally available for use in sandboxes in early December" (announced 2024-11-20); sandbox support for Agentforce and Data Cloud was GA at launch — [Salesforce Newsroom](https://www.salesforce.com/news/press-releases/2024/11/20/agentforce-testing-center-announcement/)

### Cited Findings — Evaluation and verification
- **Testing Center + AFDX test suite** "generate automated tests from sample use cases to validate instructions and topic classification," supporting CI/CD and regression testing. Recommended cycle: run the batch test, review scores and errors, inspect failures, update the agent or its test data — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html)
- Hard limits: up to **1,000 test cases** per test, up to **10 test jobs running concurrently within a 10-hour window**. Test runs **consume credits**, and tests that modify CRM data should run only in non-production environments — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html); [Trailhead](https://trailhead.salesforce.com/content/learn/modules/agentforce-specialist-certification-maintenance-summer-25/get-up-to-date-on-agentforce-concepts)
- Trailhead warns that testing agents in production can modify CRM records and consumes API requests and credits — [Trailhead](https://trailhead.salesforce.com/content/learn/modules/agentforce-specialist-certification-maintenance-summer-25/get-up-to-date-on-agentforce-concepts)
- **Observability**: the Session Tracing Data Model (STDM) objects — `AIAgentSession`, `AIAgentInteraction`, `AIAgentInteractionStep` — "capture turns, reasoning, actions, errors, and responses for debugging and root-cause analysis." Plus Agentforce Analytics, Utterance Analysis (adoption, feedback, usage, **unhandled requests**), and Agentforce Optimization, which groups interactions into "Moments" for quality analysis. Operational monitoring covers latency, token cost, API error rates — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html)
- A contemporaneous reviewer at Testing Center's launch noted it "doesn't have workflow-specific insights where developers can see the specific choices in API, data or model the agents used" — [Salesforce Launches 'First-of-Its-Kind' Agentforce Testing Center, SalesforceBen](https://www.salesforceben.com/salesforce-launches-first-of-its-kind-agentforce-testing-center/). The STDM objects above appear to address this, but I found no source explicitly confirming that.

### Cited Findings — Pricing and packaging (the most-criticized of the five)

An org picks one consumption model, never both — [Agentforce Pricing 2026: Every Model, With the Math, supered.io](https://www.supered.io/blog/agentforce-pricing/); [Aquiva](https://aquiva.com/blog/agentforce-pricing-gets-a-long-overdue-fix-flex-credits-are-now-live); [getclientell](https://www.getclientell.com/guides/agentforce-pricing-explained)

- Analyst signal on pricing uncertainty: "Salesforce customers wait for more consistent Agentforce pricing" per Evercore — [Seeking Alpha](https://seekingalpha.com/news/4425265-salesforce-customers-wait-for-more-consistent-agentforce-pricing-evercore)

### Cited Findings — Adoption failure patterns
- By May 2025, only about **8,000 of Salesforce's 150,000+ customers** had started leveraging Agentforce — [oliv.ai](https://www.oliv.ai/blog/salesforce-agentforce-reviews-analyzed)
- A **July 2026 analyst downgrade** is reported, with customer checks finding deployments **stalled at proof of concept**. Single secondary source; treat as unconfirmed — [oliv.ai](https://www.oliv.ai/blog/salesforce-agentforce-reviews-analyzed)
- Deployment timelines diverge wildly by source: 2–5 weeks; 4–6 weeks for single use cases and 8–16 weeks for complex rollouts; and **5–11 months for production rollouts that usually need a systems integrator** — [salesrobot](https://www.salesrobot.co/blogs/agentforce-review); [default.com](https://www.default.com/post/salesforce-agentforce-review-and-pricing); [oliv.ai](https://www.oliv.ai/blog/salesforce-agentforce-reviews-analyzed)
- Data readiness is a recurring blocker: a G2 reviewer wrote that Agentforce "can feel complex to set up and depends heavily on cleanup data to perform well" — [oliv.ai](https://www.oliv.ai/blog/salesforce-agentforce-reviews-analyzed)

### Inferences
- The explicit-activation step is the single most benchmark-aligned primitive any big vendor ships: it is exactly "merge deploys dark; a separate human-attested flag flip is the release." What Salesforce does *not* do is bind that activation to a review record, or require any evidence that the new version passed anything.
- Salesforce's knowledge re-indexing requirement for sandbox RAG means test results in sandbox are not guaranteed to reflect prod behavior — a structural limit on pre-release verification that the docs acknowledge only in passing.
- Credit-consuming tests plus a 1,000-case / 10-concurrent-job ceiling means regression suites have a direct marginal cost. That is an economic disincentive to thorough verification, and it is a differentiation opening: a consulting offering whose verification is deterministic and local does not meter its own test runs.
- The adoption data (8,000/150,000; PoC stall) is consistent with the thesis that creation is easy and *getting to production responsibly* is the bottleneck — which is precisely the services gap.

## OpenAI: AgentKit, Agent Builder, ChatGPT Enterprise

### Takeaway
**This is the date-critical finding of the whole report: OpenAI is shutting Agent Builder down.** OpenAI's own deprecations page lists Agent Builder as announced 2026-06-03 with a shutdown date of **2026-11-30** — roughly five weeks from this research date and about thirteen months after its October 2025 launch. The Evals platform is reported to be winding down on the same date. Of the five vendors, OpenAI is the only one that had a credible visual agent-builder plus a genuinely good eval product (trace grading against forbidden actions and citation accuracy) and is **removing both**. The governance story is now "use the Agents SDK and write code," or "use Workspace Agents in ChatGPT and accept the hosted model."

This is strong material for a consulting offering whose artifacts are the org's own reviewed code and review records rather than a vendor's proprietary graph.
- "Export produces SDK code, not a converted graph" is the lock-in tell: the visual definition was never a portable artifact.

## AWS: Bedrock Agents / AgentCore

### Takeaway
AgentCore is the most *modular* and most developer-gated of the five, and it quietly contains the single strongest match to the benchmark's review model: **AgentCore Registry "provides a governed workflow for publishing, reviewing, and approving resources."** It also has the most rigorous permission enforcement — **AgentCore Policy intercepts every tool call before execution** using a Cedar-compatible policy language — and the cleanest staged-rollout primitive (versioned configuration bundles plus A/B traffic splitting via Gateway). The cost is skill floor: there is no business-user entry point at all.

### Cited Findings — Architecture and services (from AWS primary docs)
All from [What is Amazon Bedrock AgentCore?, AWS docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html):
- Positioning: "an agentic platform for building, deploying, and operating highly effective agents securely at scale using any framework and foundation model... enable agents to take actions across tools and data with the right permissions and governance."
- **Harness** — managed agent loop; define and invoke an agent in a single API call with model, system prompt, and tools inline. "Each session runs in an isolated microVM with filesystem and shell access." Works with Amazon Bedrock, OpenAI, Google Gemini, and any OpenAI-compatible provider.
- **Runtime** — serverless, "true session isolation, built-in identity"; works with CrewAI, LangGraph, LlamaIndex, Google ADK, **OpenAI Agents SDK**, Strands; any FM in or outside Bedrock; MCP and A2A protocols.
- **Memory** — short- and long-term, "complete control over what the agent remembers," shareable memory stores across agents.
- **Gateway** — converts APIs, Lambda functions, and existing services into MCP-compatible tools, and connects to existing MCP servers.
- **Identity** — "agent identity, access and authentication management... compatible with existing identity providers" (Cognito, Okta, Entra ID, Auth0) "eliminating needs for user migration or rebuilding authentication flows."
- **Code Interpreter** and **Browser** — isolated sandboxes for code execution and web interaction.
- **Observability** — "a unified view to trace, debug and monitor agent performance in production... inspect an agent's execution path, **audit intermediate outputs**, and debug performance bottlenecks and failures," emitted in OpenTelemetry-compatible format.
- **Payments** — microtransactions via x402 / Machine Payments Protocol, with "configurable spending limits."
- **Evaluations** — "purpose-built evaluation service for automated, consistent, and data-driven agent assessment... measures how well your agents and tools execute tasks, handle edge cases, and maintain output reliability across diverse inputs and contexts... **ensures your agent meets functional and behavioral standards before and after deployment**." Supports evaluation on sessions, traces, and spans from Strands or LangGraph instrumented with OpenTelemetry or OpenInference.
- **Optimization** — "uses AI-generated recommendations, **versioned configuration bundles**, and **A/B testing** to improve agent performance through data-driven configuration changes... validate them with controlled experiments." Supports system-prompt and tool-description optimization with **traffic splitting through AgentCore Gateway**.
- **Policy** — "deterministic control to ensure agents operate within defined boundaries and business rules." Rules authored "using natural language or a policy language — **Dogwood**, which is compatible with **Cedar**." "Integrates with AgentCore Gateway, to **intercept every tool call before execution**. You can define which tools agents can access, what actions they can perform, and under what conditions."
- **Registry** — "a centralized catalog for discovering and managing agents, MCP servers, tools, skills and custom resources across your organization. Registry provides a **governed workflow for publishing, reviewing, and approving resources**, with hybrid semantic and keyword search." Works with resources "deployed on AWS, On-Prem or on any other Cloud environment."
- AWS explicitly names "Agent Platforms" as a build target: "Provide your internal developers or customers with a **paved path** to build and deploy agents using approved tools, shared memory stores, and governed access to enterprise services."
- Pricing: "flexible, **consumption-based pricing** with no upfront commitments or minimum fees" — [AgentCore pricing](https://aws.amazon.com/bedrock/agentcore/pricing/)

### Cited Findings — Policy, versioning, observability detail (secondary sources)
- Cedar policies are "evaluated on calls through the Gateway, including every tool call; **default deny, forbid wins**" — [Amazon Bedrock AgentCore Policy Implementation Guide, hidekazu-konishi.com](https://hidekazu-konishi.com/entry/amazon_bedrock_agentcore_policy_implementation_guide.html)
- **Log-only mode**: "Policy also supports a log-only mode that evaluates requests against defined policies without blocking them. - Agents-as-code via CDK: "model selection, tool configuration, session policy, and permissions — all as code, all versioned, and all deployed through the same CI/CD pipelines as other Infrastructure-as-Code components," with traffic splitting between agent variants and "rollback options if metrics deviate" — [AWS Bedrock AgentCore Limits Agent Strategies, cloudmagazin](https://www.cloudmagazin.com/en/2026/05/03/amazon-bedrock-agentcore-cli-deployment-ki-agenten/) (reports "generally available at the end of April 2026"; **not confirmed against AWS release notes**)
- Policy GA reported as **2026-03-03 in 13 AWS Regions** — [aperion.ai](https://aperion.ai/blog/aws-bedrock-agentcore-governance-guide/) — **single secondary source, unconfirmed**
- Audit trail: "Every enforcement decision is logged through Amazon CloudWatch metrics and logs, giving security and compliance teams a continuous audit trail of policy evaluations" — [AWS Builder Center](https://builder.aws.com/content/3CxHW4mko7LqnlIpujmHc46hoqF/aws-bedrock-agentcore-controls-governance-and-the-architectural-decisions-that-shape-everything-else)
- **Observability has a silent-gap footgun, documented by AWS:** "To view metrics, spans, and traces for AgentCore, you need to perform a one-time setup process to enable CloudWatch Transaction Search." Policy observability appears under the AgentCore Gateway tab in CloudWatch gen AI observability — [Amazon Bedrock AgentCore generated observability data, AWS docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-service-provided.html)
- Tracing is built on AWS X-Ray and OpenTelemetry, "covering the full request path from the initial invocation through model inference and every tool call" — [AWS Builder Center](https://builder.aws.com/content/3CxHW4mko7LqnlIpujmHc46hoqF/aws-bedrock-agentcore-controls-governance-and-the-architectural-decisions-that-shape-everything-else)
- AWS has published AgentOps guidance for operating agents at scale — [AgentOps: Operationalize agentic AI at scale with Amazon Bedrock AgentCore, AWS ML Blog](https://aws.amazon.com/blogs/machine-learning/agentops-operationalize-agentic-ai-at-scale-with-amazon-bedrock-agentcore/); tool-access governance guidance — [Govern AI agent tool access with Amazon Bedrock AgentCore Gateway](https://aws.amazon.com/blogs/machine-learning/govern-ai-agent-tool-access-with-amazon-bedrock-agentcore-gateway/)

### Inferences
- **Who builds: developers, full stop.** There is no AgentCore equivalent of Copilot Studio's Zone 1 or Google's Agent Designer. The skill floor is "can write and deploy CDK/IaC and instrument OpenTelemetry." This means AWS has no agent-sprawl problem of the Gartner kind *and* no business-user adoption story — the opposite trade from Microsoft and Google.
- **Policy is the only vendor mechanism found that is architecturally equivalent to the benchmark's query-time declarative guardrails with deny-wins**: deterministic (explicitly "outside the model"), interposed on every tool call before execution, default-deny, forbid-overrides-permit, and authored in a real policy language kept in version control. The benchmark's star-schema permission model with deny-wins is a *data-access* analogue of the same idea; AgentCore Policy is the *tool-invocation* analogue.
- **Registry's publish/review/approve workflow is the single closest big-vendor match to the benchmark's review ceremony** — and it is worth noting that the vendor who built it is the developer-only one. That supports the thesis that review machinery is built where engineers are the users, and omitted where business users are.
- **Log-only mode is a double-edged primitive.** It is good practice for rollout, and it is also exactly the configuration in which a policy fault produces no enforcement and no loud failure. AWS does not document a third state distinguishing "denied" from "policy could not be evaluated."
- The CloudWatch Transaction Search prerequisite is the same class of defect as Microsoft's firewall interaction: a verification/observability surface that is silently empty until someone performs a separate setup step. Nothing reports "observability unavailable" as a distinct state.

### Gaps
- **The primary AWS overview page states no GA/Preview status for any of the thirteen services.** Harness, Evaluations, Optimization, Policy, Registry and Payments all read as shipped product in the docs, but I could not confirm GA from AWS release notes. All GA dates above are secondary and inconsistent.
- No information found on whether the **older Bedrock Agents** service is deprecated, in maintenance, or superseded by AgentCore. The AgentCore overview does not mention it. **This needs a follow-up** — it matters for anyone with existing Bedrock Agents.
- No pricing detail retrieved beyond "consumption-based"; the pricing page itself was not fetched.
- No practitioner-complaint corpus found for AgentCore (it is newer and developer-only; community volume is low).

## CROSS-CUTTING: Which vendor has the strongest agent-lifecycle governance story?

### Takeaway
**Microsoft wins on breadth and documented completeness; AWS wins on the specific primitives that matter most for governed deployment; Salesforce wins on one crucial idea (deploy ≠ release).** No single vendor has all three. Nobody ties them together into an enforced gate.

### Cited Findings
**Microsoft — strongest overall breadth.** It is the only vendor shipping all of: (a) mandated dev/test/prod environments with managed-solution read-only enforcement downstream — [ALM strategy](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/alm); (b) three CI/CD options spanning citizen-dev to Azure DevOps with static analysis — [ALM strategy](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/alm); (c) a **risk-and-complexity tiered build model** with "IT-admin approval to publish agents" written into the Zone 2 governance column — [sec-gov-phase2](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase2); (d) a tenant-wide **Agent Registry** with an admin **activation approval gate** reviewing "description, owner, data, and tools," audience scoping, and permission consent — [agent-actions](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions?view=o365-worldwide); (e) **policy templates** binding Entra/Purview/Defender/SharePoint controls at activation time — [agent-actions](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions?view=o365-worldwide); (f) 30-day soft delete with restore and **audit-logged delete/restore events** — [agent-actions](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions?view=o365-worldwide); (g) ownership lifecycle including orphan reassignment and multi-owner continuity — [agent-actions](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions?view=o365-worldwide); (h) **conditions-based lifecycle automation rules** and sync of externally-built agents into the registry, both included in base plans — [Agent 365 service description](https://learn.microsoft.com/en-us/office365/servicedescriptions/microsoft-agent-365/microsoft-agent-365); (i) continuous config drift evaluation with quarantine via the Copilot Studio Kit Compliance Hub — [kit-overview](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/kit-overview)
**AWS — strongest specific primitives.** The only vendor with a documented "governed workflow for publishing, reviewing, and approving resources" (Registry), deterministic policy intercepting **every tool call before execution** with default-deny (Policy/Dogwood/Cedar), versioned configuration bundles with A/B traffic splitting (Optimization), and an evaluation service explicitly scoped to "before and after deployment" — all [AWS AgentCore docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html)
**Salesforce — strongest release discipline.** "Deployment does not make an agent live. A system administrator must explicitly 'activate' it," plus one-active-version constraint, canary release to a user subset, and rollback by re-activating last known good — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html)
**Google — strongest runtime containment and continuous evaluation,** weakest pre-release: Registry GA 2026-06-18, Gateway GA 2026-06-18, Observability GA 2026-06-18 — but revisions/traffic splitting only **public preview** as of 2026-05-19 with no GA date, and no approval or rollback workflow described in the primary agents documentation — [release notes](https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes); [Agents overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/agents)
**OpenAI — weakest, and shrinking.** No environments, no approval workflow, no change audit; and its builder and eval products shut down 2026-11-30 — [OpenAI Deprecations](https://developers.openai.com/api/docs/deprecations)

### Inferences
- The honest ranking depends on what "governance" means. For *who may use which agent and can we prove it* — Microsoft, decisively, because of Purview/Entra/Defender integration and the registry. For *can a bad change reach production* — AWS, because of Registry review plus versioned bundles plus traffic splitting. For *is release a separate human decision* — Salesforce. For *can we catch it misbehaving in prod* — Google.
- Every vendor's gate is **a permission to exist, not a verdict on quality.** Microsoft's activation reviews metadata (description, owner, data sources, tools) — not behavior. AWS Registry approves a *resource listing*. Salesforce activation is an admin click with no required evidence. None requires that any test ran, let alone passed.

### Gaps
- No Forrester commentary on agent lifecycle governance was retrieved in this research; only Gartner. A Forrester Wave or equivalent on agent governance platforms, if one exists, is unexamined.

## CROSS-CUTTING: What is the common weakness across all big-vendor platforms?

### Takeaway
**The hypothesis holds, with one important refinement.** All five optimize for ease of creation and under-serve review and verification — but the sharper, more defensible version of the claim is: **every vendor has substantial *evaluation* tooling and none of it is a *gate*.** Tests exist; nothing blocks on them. And no vendor distinguishes "this was denied" from "this could not be determined."

### Cited Findings — Evidence the gating is advisory, not enforced
- Microsoft's own testing doc uses advisory verbs throughout: "**consider** including automated testing as part of your deployment pipeline," "**Automate where possible**." Nothing in the ALM or activation documentation conditions publication on a test result — [sec-gov-phase4](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase4); [agent-actions](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions?view=o365-worldwide)
- Microsoft's activation review is a **metadata** review — "description, owner, data, and tools" — not a behavioral one — [agent-actions](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions?view=o365-worldwide)
- Microsoft's at-scale test automation lives in the **Copilot Studio Kit**, a separate accelerator, not the core product — [sec-gov-phase4](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase4); [kit-overview](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/kit-overview)
- Salesforce's architecture guidance describes **no formal human approval workflow**; the closest controls are automated E2E quality gates and the activation step — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html)
- Google's primary agents documentation describes **no approval workflow and no rollback**, and the staged-rollout primitive was still public preview — [Agents overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/agents); [release notes](https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes)
- OpenAI shipped the best answer-level graders (tool selection, **citation accuracy**, **forbidden actions**) and is **removing the product** on 2026-11-30 — [Introducing AgentKit](https://openai.com/index/introducing-agentkit/); [OpenAI Deprecations](https://developers.openai.com/api/docs/deprecations)

### Cited Findings — Evidence that verification itself is LLM-judged (self-review)
- Microsoft's "quality test method" scores "relevance, **groundedness**, completeness, and abstention" — model-graded criteria — [sec-gov-phase4](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase4)
- Google's Agent Evaluation is "continuous multi-turn **autoraters** on live traffic," its Anomaly Detection uses "**LLM-as-a-judge** to flag unusual reasoning," and its GenAI Evaluation Service uses **Auto SxS** — [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform); [Agents overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/agents)
- AWS Optimization uses "**AI-generated recommendations**" to change agent configuration, validated by A/B test — [AgentCore docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html)
- Only AWS Policy is explicitly framed as **deterministic** and outside the model — [AgentCore docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html); [AWS Builder Center](https://builder.aws.com/content/3CxHW4mko7LqnlIpujmHc46hoqF/aws-bedrock-agentcore-controls-governance-and-the-architectural-decisions-that-shape-everything-else)

### Cited Findings — Evidence of silent-failure / fail-opaque modes
- **Microsoft:** admin governance actions from the M365 admin center **fail** against agents behind Power Platform Firewall in active enforcement mode. The permissive setting (audit-only) is the one in which admin actions succeed — [agent-actions](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions?view=o365-worldwide)
- **Microsoft:** sharing is **not solution-aware**, so the control over who can see a production agent is configured by hand outside the ALM pipeline — [ALM strategy](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/alm)
- **AWS:** AgentCore metrics, spans and traces do not appear at all until a separate one-time CloudWatch Transaction Search setup is performed — the observability surface is silently empty until then — [AgentCore observability docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-service-provided.html)
- **AWS:** Policy log-only mode "evaluates requests against defined policies without blocking them" — a legitimate rollout mode that is also an unenforced one — [AWS Builder Center](https://builder.aws.com/content/3CxHW4mko7LqnlIpujmHc46hoqF/aws-bedrock-agentcore-controls-governance-and-the-architectural-decisions-that-shape-everything-else)
- **Salesforce:** sandbox RAG requires knowledge sources to be "ingested and re-indexed," so sandbox test results are not guaranteed to reflect production retrieval behavior — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html)
- **Practitioner corroboration:** a Hacker News thread notes that "once you give an agent tools, it gets ambient authority over all of them," making task-scoped permissions hard to express — [HN discussion on authorization for AI agents](https://news.ycombinator.com/item?id=46270697)
- **Practitioner corroboration:** a paper-linked HN thread argues organizations can increasingly prove *what* AI systems did but "cannot reliably prove who owned decisions at runtime, or whether meaningful human judgment was exercised" — [External AI Representations and the Evidentiary Gap in Enterprise Governance, HN](https://news.ycombinator.com/item?id=46838336)
- **Practitioner corroboration:** one practitioner reports that after a "full agent" approach they got "impressive demos but constant production incidents," and moved to "constrained workflows with human checkpoints" — [HN](https://news.ycombinator.com/item?id=47139978)
- **Practitioner corroboration:** in a thread on enterprise "pilot hell," a commenter describes a demo that "look[ed] very nice even though there was still a lot of unseen work to do," after which "management then assumed the project was ready to ship" — [Enterprises are getting stuck in AI pilot hell, HN](https://news.ycombinator.com/item?id=44221695)

### Inferences
- **Refined common weakness, in three parts:**
  1. **Evaluation exists but never gates.** Every vendor ships eval tooling; no vendor makes a passing eval a precondition of publication. The approval gates that exist (Microsoft activation, AWS Registry review) approve *metadata and existence*, not *behavior*.
  2. **Verification is predominantly model-graded.** Microsoft's quality method, Google's autoraters and LLM-judge anomaly detection, AWS's AI-generated optimization recommendations — the thing checking the agent is another model. Only AWS Policy is explicitly deterministic, and it governs tool access, not output correctness.
  3. **There is no tri-state failure semantics anywhere.** No vendor documentation found distinguishes *denied by policy* from *policy could not be evaluated*, or *check failed* from *check could not run*. AWS's log-only mode and CloudWatch setup prerequisite, and Microsoft's firewall interaction, are all cases where the absence of enforcement or evidence looks identical to compliance.
- A fourth, less-expected weakness: **no vendor computes risk mechanically.** Microsoft's zones come closest to risk tiering, but the tier follows the *tool the maker chose*, which the maker chooses. Nothing derives blast radius from what the agent actually reads or writes.
- A fifth: **change attribution is thin.** Microsoft audit-logs delete/restore/permanent-delete events and Google logs agent activity; I found no vendor documentation of a durable, queryable record of *who changed an agent's instructions, knowledge, or tool grants, and when, and who approved it.* Ownership is tracked; edit history is not documented as a governance artifact.
- The one place the hypothesis is **too harsh**: these platforms are not naive about *runtime* wrongness. Google's anomaly/threat detection, AWS's Policy and Observability, Salesforce's STDM and Utterance Analysis unhandled-request reporting, and OpenAI's forbidden-action graders are all real answers to "what if it's wrong." The gap is specifically *pre-release* and *attributable*, not *detective*.

### Gaps
- I could not find any vendor documentation that explicitly rules out publication on a failed eval. Absence of documentation is not proof of absence of capability; a hands-on check of a tenant would settle it and was out of scope.
- No source found on whether any vendor supports a mandatory human sign-off bound to a specific agent version hash.

## CROSS-CUTTING: Is "agent sprawl" a documented, named problem?

### Takeaway
**Yes — it is named, quantified, and framed by Gartner as of 2026-04-28, and every one of the five vendors has shipped a registry in response.** The analyst framing and the vendor response converge on *inventory and identity*, and both stop short of governing *how agents are built*.

### Cited Findings — Gartner
- Gartner published "Six Steps to Manage AI Agent Sprawl" on **2026-04-28** — [Gartner press release](https://www.gartner.com/en/newsroom/press-releases/2026-04-28-gartner-identifies-six-steps-to-manage-artificial-intelligence-agent-sprawl) (direct fetch returned 403; content below is from secondary summaries)
- **The six steps**, per secondary summary: (1) **Set governance policies** defining who can build and share agents and which external connectors they may use; (2) **Build a central agent inventory** using AI TRiSM tools to find and catalog all agents, including **shadow AI agents** deployed outside IT; (3) **Define identity, permissions, and lifecycle** — give each agent an identity, explicit access rights, a **review schedule**, and a **retirement path**; (4) **Develop AI information governance** specifying what data each agent can access, who controls that access, and how stale data is handled; (5) **Monitor and remediate behavior** — track what agents actually do and catch **drift from their intended scope**; (6) **Foster responsible AI usage** through training and communities of practice — [Gartner Identifies Six Steps to Manage AI Agent Sprawl, Enterprise DNA](https://enterprisedna.co/resources/news/gartner-ai-agent-sprawl-six-steps-enterprise-2026/)
- **Statistics:** the average Fortune 500 company ran **fewer than 15 AI agents in 2025**; Gartner predicts Fortune 500 companies will run **more than 150,000 agents by 2028** — described as a ~10,000x increase in three years. As of April 2026, **only 13% of organizations believe they have the right AI agent governance in place** — [Enterprise DNA](https://enterprisedna.co/resources/news/gartner-ai-agent-sprawl-six-steps-enterprise-2026/); [Gartner Predicts AI Agent Sprawl and Outlines Prevention Steps, tech.co](https://tech.co/news/gartner-steps-governing-ai-agents)
- Named analyst: **Max Goss, Senior Director Analyst, Gartner**, who per the summary says organizations must balance governing agents and managing sprawl with safely letting employees innovate (**paraphrase, not a direct quote**) — [Enterprise DNA](https://enterprisedna.co/resources/news/gartner-ai-agent-sprawl-six-steps-enterprise-2026/)
- Gartner reportedly warns **against uniform, one-size-fits-all governance**, since agents operate at different autonomy levels and trust boundaries, and favors balanced governance over blanket restriction — [Gartner flags rising AI agent sprawl, Digital Tech Circle](https://digitaltechcircle.in/gartner-flags-rising-ai-agent-sprawl-outlines-six-step-governance-framework/)
- Gartner reportedly predicts that **by 2027, 40% of enterprises will demote or decommission autonomous agents due to governance gaps** — **secondary source only, not confirmed in the press release** — [refontelearning](https://www.refontelearning.com/blog/ai-agent-sprawl-governance)
- Sprawl is characterized as "a tangle of autonomous AI tools that creates misinformation, data loss, and IT complexity risks" — [The Register, 2026-04-30](https://www.theregister.com/software/2026/04/30/govern_your_bots_carefully_or_chaos_could_ensue/5229506)

### Cited Findings — Every vendor shipped a registry in response
- **Microsoft:** Agent Registry in the M365 admin center, inventory included in base plans, with sync of externally-built agents, "conditions-based rules" lifecycle automation, and Defender **shadow-AI endpoint agent sync** plus Intune **blocking of unsanctioned local endpoint agents** — [Agent 365 service description](https://learn.microsoft.com/en-us/office365/servicedescriptions/microsoft-agent-365/microsoft-agent-365)
- **Microsoft:** inventory is explicitly pitched at hygiene — find "custom agents created by users who left" and "inactive agents to clean up" — [Power Platform release plan](https://learn.microsoft.com/en-us/power-platform/release-plan/2025wave1/power-platform-governance-administration/search-inventory-custom-agents-copilot-studio); and the Kit Compliance Hub auto-creates compliance cases with quarantine/delete enforcement — [kit-overview](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/kit-overview)
- **Google:** Agent Registry, GA 2026-06-18, "centralized view to manage and audit all Google-made, employee-built, and third-party agents" — [release notes](https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes); [Google Cloud Community](https://security.googlecloudcommunity.com/cloud-security-foundation-7/architecting-gemini-enterprise-for-regulated-industries-security-insights-from-next-26-7430)
- **AWS:** AgentCore Registry, "centralized catalog for discovering and managing agents, MCP servers, tools, skills and custom resources across your organization," including resources on-prem and on other clouds — [AgentCore docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html)
- **OpenAI:** Connector Registry as the admin layer for data/tool connections across ChatGPT and the API — [Introducing AgentKit](https://openai.com/index/introducing-agentkit/)
- **Analyst/practitioner adoption signal:** a developer building runtime governance tooling reports "adoption is slow, but interest is growing," attributing it partly to the lack of US regulation and to companies "still struggling to define the ROI on their AI ambitions" — [HN](https://news.ycombinator.com/item?id=49827032)

### Inferences
- The industry consensus answer to sprawl is **a registry plus an identity plus a retirement path**. That is *asset management for agents*. It answers "how many do we have, who owns it, can we kill it."
- It does **not** answer "is this one any good," "was it reviewed," or "what did it get wrong last Tuesday." Gartner's own step 3 asks for a **review schedule** and step 5 for **drift detection** — the two steps vendors cover least. Microsoft's Compliance Hub config-drift checks are the nearest thing shipped, and they check *configuration* against thresholds, not *behavior* against expectations.
- The <15 → 150,000 projection, if even directionally right, makes per-agent human review economically impossible and makes *risk-proportionate* review the only viable model. Gartner's explicit warning against one-size-fits-all governance is an analyst endorsement of exactly that. This is the strongest external validation available for a tiered-ceremony approach.
- Agent sprawl is a **downstream symptom of the thing the big vendors optimized for.** Microsoft's Zone 1 ("Anyone can make... agents") and Google's no-code Agent Designer are sprawl generators by design, with the registry bolted on afterward as the remedy. AWS, which never built a business-user entry point, is also the vendor whose Registry has a review workflow.

### Gaps
- **The Gartner press release could not be fetched directly (HTTP 403), and The Register's article URL 404'd.** All six-step wording, statistics and the Goss attribution are from secondary summaries. The "fewer than 15" baseline, the ">150,000 by 2028" projection, the "13%" governance figure and the "40% by 2027" prediction should be verified against the Gartner release or a Gartner subscription before publication.
- No Forrester material on agent sprawl was found.

## CROSS-CUTTING: Do any vendors treat agent-building as requiring engineering rigor?

### Takeaway
**It is split, and the split is explicit and documented — not accidental.** Microsoft formally stratifies agents into three risk zones where the top zone gets full ALM and the bottom zone is explicitly treated as low-stakes configuration. AWS treats all agent building as engineering because it has no other mode. Salesforce treats it as engineering in its architecture guidance while shipping an admin-facing builder. Google and OpenAI's no-code surfaces assume low-stakes configuration.

### Cited Findings
- **Microsoft states the stratification outright.** Zone 1: "Anyone can make personal and team productivity agents based on content they already have access to. Agents have read-only permissions and stay private" — low risk, low complexity, safe defaults. Zone 3: "Pro developers build mission-critical, enterprise-grade agents... uses organizational standard ALM practices and the strongest security controls." Zone 2 sits between and explicitly requires "formal assistance and oversight from a coach" — [sec-gov-phase2](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase2)
- Microsoft's ALM golden rules read as engineering discipline: no customizing outside dev, always work in solutions, custom publisher and prefix, environment variables for secrets, export as managed, automate ALM — [ALM strategy](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/alm)
- **AWS treats agents as code, period.** Agent definitions, "model selection, tool configuration, session policy, and permissions — all as code, all versioned, and all deployed through the same CI/CD pipelines as other Infrastructure-as-Code components" — [cloudmagazin](https://www.cloudmagazin.com/en/2026/05/03/amazon-bedrock-agentcore-cli-deployment-ki-agenten/); and AWS's stated use case is building a "**paved path**" for internal developers with approved tools and governed access — [AgentCore docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html)
- **Salesforce treats it as a software lifecycle in guidance:** agents are metadata in Git as "the single source of truth," new version per change, scratch org → sandbox → prod, CI/CD quality gates, canary release, rollback by re-activation — and notes the lifecycle "requires broader skills across data science, ML engineering, and agent development" — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html)
- **Google offers both and governs them differently by edition:** Business edition includes a "no-code Agent Designer"; support for custom and third-party agents plus "advanced security, governance" is reserved for Standard/Plus — [agentmarketplace.ai](https://agentmarketplace.ai/blog/gemini-enterprise-pricing); [workagent.ai](https://workagent.ai/gemini-enterprise-pricing). Agent Studio logic can be exported to ADK, implying an intended graduation path from configuration to code — [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform)
- **OpenAI's answer is now "write code":** the migration path from the deprecated visual Agent Builder is the Agents SDK, and "the built-in export produces Agents SDK code, not a converted graph" — [OpenAI Deprecations](https://developers.openai.com/api/docs/deprecations); [reflektlab](https://reflektlab.ai/blog/openai-agent-builder/)
- **Practitioner evidence that the low-stakes assumption fails in production:** "after trying 'full agent' approach... impressive demos but constant production incidents," resolved by moving to "constrained workflows with human checkpoints" — [HN](https://news.ycombinator.com/item?id=47139978)

### Inferences
- The industry has converged on a **two-population model**: business users configure low-blast-radius agents with safe defaults, engineers build high-blast-radius ones with ALM. Nobody has solved the middle, which is where the money and the risk both are — Microsoft's own Zone 2 answer is "assign a human coach," which is a staffing solution, i.e., a consulting engagement described in a vendor doc.
- The assignment of an agent to a rigor tier is **always self-selected** (by which tool the maker opens, or which edition the org bought). The benchmark's mechanical risk tier computed from changed file paths has no counterpart in any vendor platform found here.
- OpenAI's deprecation is the strongest available argument that no-code agent configuration is not yet a durable enterprise artifact: the vendor that bet hardest on it reversed in thirteen months and offers no graph conversion.

### Gaps
- Could not establish whether Microsoft's Zone 2 "IT-managed review processes" and "IT-admin approval to publish agents" are enforced by product mechanism or are process guidance the org must implement. The doc lists them in a governance column without naming the enforcing feature — **this is the single most important open question for competitive positioning against Microsoft** and should be verified hands-on in a tenant.

## WHAT THE BIG VENDORS DO THAT THE BENCHMARK DOES NOT

### Takeaway
The vendors are far ahead on **identity for agents, runtime interception, production detection, compliance/legal plumbing, and inventory of things the benchmark's process never touched** — including third-party and shadow agents.

### Cited Findings
1. **Agents as first-class identity principals.** Google issues each agent a **SPIFFE-formatted cryptographic ID that can receive IAM permissions** — [Agents overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/agents). Microsoft has **Entra Agent IDs** with lifecycle policies, conditional access, identity protection and "sponsor-driven workflows" — [Agent 365 service description](https://learn.microsoft.com/en-us/office365/servicedescriptions/microsoft-agent-365/microsoft-agent-365). AWS Identity federates to Cognito/Okta/Entra/Auth0 — [AgentCore docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html). The benchmark's permission model governs *data access*; it does not make the agent an auditable principal in the corporate directory.
2. **Policy interception on every tool call, before execution.** AWS Policy with Dogwood/Cedar: "intercept every tool call before execution," default-deny, forbid-wins — [AgentCore docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html); [hidekazu-konishi](https://hidekazu-konishi.com/entry/amazon_bedrock_agentcore_policy_implementation_guide.html). Google Agent Gateway enforces access control plus Model Armor inspection of tool calls — [Agents overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/agents). The benchmark's guardrails are enforced at *query time* over knowledge; neither has an equivalent chokepoint on *action* invocation.
3. **Production anomaly, threat and drift detection.** Google Agent Anomaly Detection (statistical + LLM-judge on unusual reasoning), Agent Threat Detection (reverse shells, bad IPs), Agent Security dashboard via Security Command Center — [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform). Microsoft Defender real-time protection for agents (Preview) and Insider Risk Management extended to agents — [agent-actions](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions?view=o365-worldwide); [Agent 365](https://learn.microsoft.com/en-us/office365/servicedescriptions/microsoft-agent-365/microsoft-agent-365).
4. **Continuous evaluation on live traffic and automated failure clustering.** Google: "continuous multi-turn autoraters on live traffic" and Agent Optimizer that "clusters real-world failures and suggests refined system instructions" — [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform). AWS Optimization: AI-generated recommendations validated by A/B test — [AgentCore docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html).
5. **Simulated-user adversarial testing as a product.** Google Agent Simulation "tests agents against synthetic users and virtualized tools," scored on task success and safety — [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform). The benchmark's adversarial refuter attacks *findings*; this attacks the *agent*.
6. **Compliance, legal-hold and data-lifecycle plumbing.** Purview audit logs plus **eDiscovery content search of agent interactions** "to export and hold for legal, regulatory, and investigative needs," Data Lifecycle Management for agent-generated data, sensitivity-label inheritance, DLP for agents, AI compliance assessment — [Agent 365 service description](https://learn.microsoft.com/en-us/office365/servicedescriptions/microsoft-agent-365/microsoft-agent-365). Plus FedRAMP High controls met (authorization pending) as of 2026-10-01 — same source.
7. **Inventory of agents the organization did not build.** Microsoft syncs agents and metadata from external, unmanaged platforms into the registry, syncs **shadow AI endpoint agents** via Defender, and can block unsanctioned local endpoint agents via Intune — [Agent 365](https://learn.microsoft.com/en-us/office365/servicedescriptions/microsoft-agent-365/microsoft-agent-365). Google's Registry covers "Google-made, employee-built, and third-party agents" plus MCP servers — [Agents overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/agents). AWS Registry covers resources "deployed on AWS, On-Prem or on any other Cloud" — [AgentCore docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html).
8. **Operational lifecycle hygiene at scale.** Microsoft's 30-day soft delete with restore, ownerless-agent reassignment, multi-owner continuity, conditions-based lifecycle automation rules, and start/stop of underlying Azure infrastructure — [agent-actions](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions?view=o365-worldwide); [Agent 365](https://learn.microsoft.com/en-us/office365/servicedescriptions/microsoft-agent-365/microsoft-agent-365).
9. **Managed runtime, sandboxing and cost controls.** Isolated microVM per session (AWS Harness), Agent Sandbox for model-generated code (Google), configurable spending limits (AWS Payments), "built-in cost controls" (Google) — [AgentCore docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html); [Welcome to Gemini at Work 2026](https://cloud.google.com/blog/products/ai-machine-learning/welcome-to-gemini-at-work-2026).
10. **Multi-tenant and federated governance.** Microsoft supports blocking agents across governed tenants under an Entra Tenant Governance relationship — [agent-multi-tenant](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-multi-tenant?view=o365-worldwide).

### Inferences
- The structural gap is **detective and infrastructural, not procedural.** The benchmark is a pre-release discipline; the vendors have built the post-release and identity layer. An independent offering that ignores agent identity, tool-call interception, and production detection will be credibly accused of governing only the part that is easy to govern.
- Concretely, the benchmark has no documented answer for: an agent as a directory principal; a chokepoint on tool invocation; eDiscovery/legal hold over agent interactions; inventory of agents built outside the program; or cost caps.

### Gaps
- Whether the benchmark already covers any of these was out of scope by instruction; this list is "what the vendors do," not a verified diff.

## WHAT THE BENCHMARK DOES THAT THE BIG VENDORS DO NOT

### Takeaway
Everything the benchmark does that is distinctive sits in one place: **it treats the authoring of an agent as a change that must earn its way to production, and it makes the earning tamper-resistant.** No vendor found in this research does any of the following.

### Cited Findings — each item below is a capability for which no vendor source was found
1. **A mechanically computed risk tier the author cannot downgrade.** Microsoft's zones are the only risk stratification found, and the tier follows the tool the maker chose, which the maker chooses — [sec-gov-phase2](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase2). No vendor derives risk from what the agent actually touches. Gartner's warning against one-size-fits-all governance makes this an unmet analyst recommendation — [Digital Tech Circle](https://digitaltechcircle.in/gartner-flags-rising-ai-agent-sprawl-outlines-six-step-governance-framework/)
2. **Review ceremony proportional to risk, as an enforced gate.** The two approval gates that exist — Microsoft's activation ("description, owner, data, and tools") and AWS Registry's "governed workflow for publishing, reviewing, and approving resources" — are uniform and metadata-level, not behavior-level and not scaled to blast radius — [agent-actions](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions?view=o365-worldwide); [AgentCore docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html)
3. **A review record bound to the head commit SHA, serving as the merge credential.** Salesforce comes closest with agents-as-metadata in Git and a separate activation step, but no source describes binding an approval to a specific version identifier or requiring it to merge — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html)
4. **Deterministic verification with LLM self-review forbidden.** The opposite is the norm: Microsoft's quality method grades groundedness/relevance/completeness/abstention — [sec-gov-phase4](https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/sec-gov-phase4); Google uses autoraters and LLM-as-a-judge — [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform); AWS Optimization uses AI-generated recommendations — [AgentCore docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html). Only AWS Policy is explicitly deterministic, and only over tool access.
5. **An unrunnable check reports SKIPPED, never PASSED.** No vendor documentation found defines this semantics. The documented reality runs the other way: AWS metrics/traces are simply absent until CloudWatch Transaction Search is enabled — [AgentCore observability docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-service-provided.html); AWS Policy log-only mode evaluates without blocking — [AWS Builder Center](https://builder.aws.com/content/3CxHW4mko7LqnlIpujmHc46hoqF/aws-bedrock-agentcore-controls-governance-and-the-architectural-decisions-that-shape-everything-else); Microsoft admin actions fail against firewalled environments — [agent-actions](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions?view=o365-worldwide)
6. **An explicit distinction between "denied" and "could not determine," so config faults fail loud.** No vendor documentation found describes tri-state authorization semantics. AWS Policy is default-deny with forbid-wins — which collapses an unevaluable condition into a deny, i.e., silent — [hidekazu-konishi](https://hidekazu-konishi.com/entry/amazon_bedrock_agentcore_policy_implementation_guide.html)
7. **Blocking findings that require a reproduction, and an adversarial agent whose job is to disprove each finding.** Google Agent Simulation attacks the agent with synthetic users — [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform); OpenAI's trace graders scored forbidden actions and citation accuracy — [Introducing AgentKit](https://openai.com/index/introducing-agentkit/). Neither applies adversarial pressure to the *review output*. No vendor has a refuter.
8. **An orchestrator protocol where the main AI session never writes production code.** No vendor source describes constraining the AI's own role in the build. The practitioner corroboration for why this matters is a HN report of moving from free-roaming agents ("impressive demos but constant production incidents") to "constrained workflows with human checkpoints" — [HN](https://news.ycombinator.com/item?id=47139978)
9. **A deferral ledger with CI enforcement.** Gartner's step 3 asks for a "review schedule" and a "retirement path" — [Enterprise DNA](https://enterprisedna.co/resources/news/gartner-ai-agent-sprawl-six-steps-enterprise-2026/). The vendor answer is retirement tooling (Microsoft soft delete, inactive-agent cleanup) — [agent-actions](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions?view=o365-worldwide); [Power Platform release plan](https://learn.microsoft.com/en-us/power-platform/release-plan/2025wave1/power-platform-governance-administration/search-inventory-custom-agents-copilot-studio). No vendor tracks accepted-but-unfixed findings as enforced debt.
10. **Dark merge plus a separate human-attested release flip, with the attestation recorded.** Salesforce's explicit activation is the closest and is genuinely the same *shape* — "Deployment does not make an agent live" — but no source describes the activation as attested, evidence-conditioned, or recorded against a review — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html)
11. **Consumers interacting via structured menus and forms rather than free-form chat, with per-result provenance.** Every vendor's delivery surface is conversational: Microsoft 365 Copilot/Teams/Outlook — [agent-actions](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions?view=o365-worldwide); the Gemini Enterprise app — [Introducing Gemini Enterprise Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform); ChatKit — [Introducing AgentKit](https://openai.com/index/introducing-agentkit/). Groundedness and citation accuracy appear as *eval criteria* (Microsoft's quality method, OpenAI's graders) rather than as per-result provenance shown to the consumer.
12. **An immutable grant audit trail.** Microsoft audit-logs soft-delete/restore/permanent-delete events with the initiating system — [agent-actions](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/agent-actions?view=o365-worldwide) — and Google logs agent activities — [Agents overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/agents). No vendor documentation found describes an immutable record of *permission grants* over time as a first-class governance artifact.

### Inferences
- The benchmark's real differentiation is **tamper-resistance and evidentiary integrity**, not features. Mechanical risk tiering, SHA-bound review records, forbidden self-review, SKIPPED-not-PASSED, and tri-state authorization are all answers to the same question: *can the author or the model quietly lower the bar?* Every vendor gate can be satisfied by an admin clicking approve on a metadata summary.
- This maps directly onto independently observed enterprise pain: the HN "evidentiary gap" argument — organizations can prove *what* AI did but not "who owned decisions at runtime, or whether meaningful human judgment was exercised" — [HN](https://news.ycombinator.com/item?id=46838336). That is a precise description of the hole the benchmark fills, voiced by someone with no stake in it.
- **Three vendor capabilities are the strongest counter-positioning arguments and should be addressed head-on rather than ignored:** AWS Registry's publish/review/approve workflow (the closest competitor to the review ceremony), AWS Policy's deny-wins interception of every tool call (the closest competitor to query-time guardrails), and Salesforce's explicit activation (the closest competitor to dark-merge-plus-flip). In each case the vendor has the *shape* and lacks the *evidence binding*.
- **Commercial opening:** the benchmark's verification is deterministic and local, so it does not meter its own test runs. Salesforce charges credits per test run and caps suites at 1,000 cases / 10 concurrent jobs — [Agent Development Lifecycle](https://architect.salesforce.com/docs/architect/fundamentals/guide/agent-development-lifecycle.html); Microsoft's credit model charges per interaction with wide variance — [thenegotiationexperts](https://thenegotiationexperts.com/blog/copilot-studio-message-pricing-costs/). Consumption pricing taxes thoroughness. That is a genuinely differentiating argument and it is well-sourced.
- **Platform-risk argument:** OpenAI's Agent Builder shutdown on 2026-11-30, thirteen months after launch, with export producing SDK code rather than a convertible graph — [OpenAI Deprecations](https://developers.openai.com/api/docs/deprecations); [reflektlab](https://reflektlab.ai/blog/openai-agent-builder/) — is the single best citable argument that an agent estate should be the org's own reviewed artifacts, not a vendor's proprietary definition format.

### Gaps
- Items above are "no source found," not "proven absent." These are large vendors with fast release cadences and heavy preview pipelines; absence of documentation is weak evidence. Each claim of absence should be hedged in the final report ("no vendor documentation found describes X" rather than "no vendor does X").
- The benchmark was not researched by instruction, so no verified feature-level diff was possible — this section compares vendor documentation against the benchmark *description supplied in the assignment*.
